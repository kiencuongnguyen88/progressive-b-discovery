# Case Study — Progressive B Discovery Used on This Repository

This is one self-hosting case from the public Git history of this repository.

It shows a real sequence:

```text
provisional direction
→ revert
→ narrower public change
→ coherence repair
```

It does **not** claim broad validation or explain private decision motives that are not visible in the public history.

---

## 1. Public evidence trail

| Commit | Publicly observable change |
|---|---|
| `73c15b2` | Added `docs/development-frontier.md` as a provisional development note. The commit message kept the stable public baseline unchanged and made no broad-validation claim. |
| `7482f92` | Reverted that provisional frontier as premature and restored the prior repository content surface while preserving Git history. |
| `70c8534` | Updated five public files for `v0.2`: bounded work vs Current B acceptance, Proposed Next B separation, workflow/manual-effort evidence, and checkpoint continuity. |
| `b1095be` | Synchronized the Quick Start and prompt pack with the `v0.2` semantics and made the evidence model more explicit. |

The first provisional frontier was much broader than the later public changes. Its file contained many advanced search, execution, frontier, convergence, and acceptance ideas.

The later repository did not simply restore that large file. It moved forward through narrower public changes.

---

## 2. Progressive B interpretation

### A proposed direction is not automatically the Current B

A real provisional direction existed in Git.

The next commit still reverted it.

That is a concrete example of:

```text
Proposed Next B
!=
Current B
```

### Rollback can preserve lineage

The revert restored the prior content surface without erasing the rejected attempt from history.

The working baseline could continue while the path remained recoverable.

### A later change can be narrower than an earlier proposal

The broad provisional frontier was followed by a smaller `v0.2` public delta.

The important point is not that every idea in the earlier frontier was wrong.

The public surface simply moved forward with a narrower set of changes.

### Coherence needs its own follow-up

After the `v0.2` semantic update, the Quick Start and prompt pack still needed synchronization.

The later `b1095be` commit aligned those user-facing surfaces.

This shows that a semantic change can still need a separate coherence pass.

---

## 3. Evidence is more than final prose

The public history contains several kinds of evidence:

- a provisional candidate;
- a revert;
- a restored working baseline;
- a narrower later change;
- a coherence repair.

This matters because Progressive B Discovery is not only about producing the next artifact.

It is also about preserving enough evidence to know:

- what was tried;
- what changed;
- what was rejected or reverted;
- what the current public surface actually contains;
- what still needs another loop.

The later Quick Start and prompt update also makes one distinction explicit:

```text
observed evidence
!=
human interpretation alone
```

Real use, tests, readback, runtime results, observed failure/repair, workflow friction, and human feedback can all contribute evidence.

## 5. Checkpoint from this case

```md
Current B:
A small public Progressive B Discovery method kit that keeps evidence, bounded work, target admission, lineage, and checkpoint continuity visible without becoming a large framework.

Observed evidence:
A broad provisional frontier was committed and then reverted as premature.
Later public changes were narrower and were followed by a coherence repair.

What works:
Git history preserves both the working baseline and the rejected path.

Keep:
Small public-method shape, recoverable lineage, bounded-work semantics, Current B admission, evidence/readback, and checkpoint continuity.

Do not infer:
That every provisional idea should later be promoted.
That Git history reveals every private decision reason.
That one self-hosting case proves broad external validation.

Next move:
Use this case as public method evidence while keeping external-user validation as a separate frontier.
```

## 6. What this case proves — and what it does not

### Supported by the public history

- a provisional direction was committed;
- that direction was reverted as premature;
- the previous content surface was restored without rewriting history;
- a later `v0.2` update was narrower than the provisional frontier;
- a further commit synchronized the public quick path.

### Not established by this case

- why every private decision was made;
- whether outside users find the method easy to use;
- whether the method is broadly validated;
- whether every rejected idea is permanently wrong;
- whether `v0.2` is the final form of the method.

External-user feedback remains a separate evidence frontier.

---

## 7. The narrow claim

This case supports one narrow conclusion:

> Progressive B Discovery has one public self-hosting history in which a broad provisional direction was preserved in Git lineage, reverted as premature, followed by a narrower public update, and then synchronized across the user-facing quick path.

That is useful evidence about the method's own development.

It is not a substitute for external validation.
